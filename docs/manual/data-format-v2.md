# JSON v2: составные элементы и словарь

Экспорт теперь использует `format: "concept-field-graph"`, `version: 2`. Виды документов, списки пространства, ID, JSON Patch истории, preview импорта и применение кандидатов сохраняются из [v1](data-format.md). Импорт читает обе версии; старые документы и SQLite-снимки не изменяются при чтении. Прежние рёбра без структурных полей остаются обычными содержательными связями, старые узлы — концептами. Программа версии `9d4fdaf` отвергнет новый v2 явно; не следует вручную подменять номер версии новым анонимным структурам.

## Структурная функция и содержательный тип

```json
{"id":"alpha-id","structure":"combination","label":"","kind":"","notes":"Ручной состав","alternatives":"","source":"Оператор","origins":[]}
```

`structure` — `concept` (по умолчанию при отсутствии поля) либо `combination`. Это функция редактора, а не семантическая категория. `kind` по-прежнему свободное содержательное / лингвистическое / ролевое пояснение. Комбинация не обязана иметь название и содержательный тип. Интерфейс показывает пустое название как `α · <короткий ID>`; это только подпись, не сохраняемое имя и не доказательство тождества. Идентичность обеспечивается полным ID. Концепт по-прежнему требует непустое название.

```json
{"id":"membership-id","from":"alpha-id","to":"component-id","role":"component","type":"","componentRole":"модификатор","notes":"Пояснение включения","origins":[]}
```

`role` — `relation` (по умолчанию) либо `component`. Включение направлено от комбинации к компоненту; компонентом может быть другая комбинация. Повторное использование, несколько включений одного компонента и циклы представимы. `componentRole` — необязательная свободная подпись. `type` может быть пустым и у обычной связи; семантическая категория не навязывается новому соединению. Содержательная связь к α относится только к α; она не дублируется на компонентах. Обход соседей для визуализации / экспорта не считается выводом.

## Словарь и след замещения

Исследование может иметь дополнительные списки `designations` и `substitutions`; их отсутствие означает пустой список без миграционной записи.

```json
{"id":"designation-id","text":"твёрдый","target":"alpha-id","notes":"Ручное решение о обозначении","source":"Оператор","origins":[],"createdAt":"2026-10-09T00:00:00+00:00"}
```

Словарь не является семантическим узлом или ребром. `target` обязан существовать в этом исследовании; одинаковый текст может адресовать разные элементы. Пустые обозначения не допускаются. Пояснение / источник / происхождение сохраняются. Поиск редактора может найти комбинацию по словарному обозначению.

Замещение сохраняет объект `substitutions` с `id`, `sourceId`, `targetId`, `reason`, `time`, `status` и полными `before` / `after`. Статус — `active`, `restored` или `archived`. `before.source` сохраняет весь исходный узел, `before.sourceIndex` — место в списке; `target`, `edges`, `designations`, `matches`, `rootId` фиксируют затронутый контекст. `after` хранит полученный контекст. Активный исходник отсутствует в графе; цель — существующая комбинация. ID перенесённых рёбер сохраняются. В `origins` комбинации и созданного обозначения сохраняется снимок исходного концепта.

Замещение выполняется только отдельной операцией `replace_concept` с `confirmed:true` и непустым обоснованием, после `/api/substitution-preview`. Новый импортированный объект `substitution` — сохранение чужого следа решения, а не команда выполнить замещение. Импорт не запускает семантическое преобразование сам по себе. Техническая пригодность / ссылки проверяются, утверждение о эквивалентности остаётся решением оператора.

`restore_substitution` возвращает исходник и ссылки только если затронутый контекст точно совпадает с `after`; иначе сообщает неоднозначность и ничего не записывает. Полное восстановление версии из истории доступно независимо от этого ограничения. В новом объединённом исследовании следы прежних замещений архивные: в них `sourceTargetId` сохраняет ID цели исходного контекста, а `targetId` адресует скопированный элемент; их снимки относятся к исходным графам, поэтому не применяются как локальная отмена.

## Кандидаты, diff и фрагменты

`changes` сохраняет операции v1 и добавляет `designation`, `substitution`, `delete_designation`, `delete_substitution`. В `study.value` теперь передаются только метаданные без `nodes`, `edges`, `designations`, `substitutions`; каждый объект этих списков — свой кандидат. Кандидаты применяются одной транзакцией с проверкой всех зависимостей. При явном удалении узла удаляются его текущие обозначения, но версии остаются в истории. Цель активного замещения удалить / превратить в обычный концепт нельзя до отмены замещения.

Включение / анонимный элемент можно предложить обычными `node` / `edge` кандидатами с новыми полями; отсутствие названия у комбинации валидно. Для текущего объекта передавайте полный `base` и остальные дополнительные атрибуты. Корректность смены структурной функции проверяется по имеющимся включениям: обычный концепт не может быть началом включения.

Полный экспорт включает словарь и следы замещения; фрагмент включает их по цели в выбранном множестве узлов. Исходные контексты в снимках происхождения / замещения намеренно остаются полными даже при фрагменте глубины 0. Diff сохраняет полные структуры и новые атрибуты; структурное сопоставление рёбер дополнительно учитывает `role` и `componentRole`, чтобы включение не смешивалось с утверждением. Версионный diff создаёт кандидатов словаря / следа изменения; обычные имена α и общие компоненты не служат основанием для подтверждения.

Пакет обратного diff также содержит явное удаление появившейся записи замещения (`delete_substitution`, с полным `base`). Исходный документ / запись остаются в архиве импорта и истории. Применение обычных кандидатов не стирает уже накопленные origins узла: для точного возврата к прежнему снимку используйте отмену замещения либо историю, а не импорт обратного diff. В импортированных контекстах проверяются наличие исходника, ID, позиции и списки объектов; некорректный контекст отклоняет весь пакет.

Минимальный пример предложения неназванной комбинации и включения (исследование `study-id` и концепт `concept-id` уже существуют):

```json
{
  "format":"concept-field-graph","version":2,"kind":"changes",
  "changes":[
    {"operation":"node","studyId":"study-id","base":null,"value":{"id":"new-alpha-id","structure":"combination","label":"","kind":"","notes":"Кандидат состава","alternatives":"","source":"Предложение для ручной проверки","origins":[]}},
    {"operation":"edge","studyId":"study-id","base":null,"value":{"id":"new-membership-id","from":"new-alpha-id","to":"concept-id","role":"component","type":"","componentRole":"","notes":"","origins":[]}}
  ]
}
```

Для реального нового объекта выберите уникальный UUID; принять узел и включение следует вместе. Никакое совпадение имён / компонентов не добавляет подтверждения эквивалентности.
