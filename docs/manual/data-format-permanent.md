# Постоянный граф: JSON и хранение M008

## v5: операторское состояние M020

Читатель принимает v1–v5 без миграции старых snapshot. Необязательный `operatorVersion: 5` обозначает состояние M020. Экспорт учитывает всю историю и импортные архивы; после reset/restore версия не понижается так, чтобы скрыть новые записи. v1–v4 документ с `operatorVersion` отклоняется. Новые поля идентичности/проверки требуют этого маркера. Структура SQLite и формат журнала не меняются.

У ручных постоянных объектов M018 допускается отсутствие `definitionId`, если имеются `origins` и операторская версия 5. Новый объект получает `operation: graph_editor`, ручной источник; revision/действие восстанавливаются из журнала. Старый `definitionId` по-прежнему требует существующий `definitionDraft`; владелец и origins не перезаписываются произвольной формой. При явном удалении исторического определения активный owner снимается у оставшихся объектов, а в origins добавляется `archive_definition` со старым ID и снимком title/definition; вся прежняя запись остаётся в истории. Новые обозначения также не требуют определения для владельца.

Дополнения `thoughtLab.drafts`:

- `sceneId` может быть задан уже в черновике. У локального элемента `sceneObjectId` — явный выбор того же объекта **этой** сцены. Его conceptId/value сверяются с объектом. Отсутствие поля означает новый независимый экземпляр, а не неизвестное автоматическое совпадение.
- `objectBindings: [{localId,objectId}]` завершённой мысли адресует фактически использованные ID сцены. Разные мысли могут разделять objectId после явного выбора. Первоначальные `thoughtId/localId` на созданном объекте обозначают происхождение, не эксклюзивное владение. При удалении создавшей мысли у оставшегося объекта происхождение превращается в `originThought: {id,text,localId}`; live-применения адресуют его через objectBindings.
- `bindingRequired: bool` и `contentEdges: [localEdgeId]` у позиции — операторское требование содержательной привязки и выбранные инцидентные обычные использования. Требование входит в шаблон/contract, а конкретный набор связей допускает уточнение к другому содержанию. Включённая позиция с требованием должна иметь включённое выбранное отношение. Это не тип постоянного концепта и не схема предметных ролей.
- `representation: {confirmed,digest,revision}` — отдельное решение о полноте конкретного представления. `thought_confirm` проверяет обязательность, необходимые привязки и покрытие непробельных Unicode code points текста anchors к включённым ID. Затем закрепляет digest текста, конфигурации и anchors (без координат). Обычное сохранение изменённого содержания снимает подтверждение; напрямую назначить его через save нельзя. `thought_complete` проверяет digest повторно.
- Прежний завершённый v4 разбор без representation читается без приписывания новой проверки. Новое завершение требует её. `thought_revise` создаёт отдельный черновик с `revisedFrom` и снятыми sceneObjectId, не переписывает событие.
- После удаления шаблона `templateArchive` хранит его ID, версию применения и закреплённый contract. `templateRef` разрешается этим снимком, когда шаблона больше нет в библиотеке. Содержательные постоянные ссылки архивного контракта остаются защищёнными.

Новые операции `thought_close`, `thought_revise`, `thought_confirm` используют прежнюю общую revision-транзакцию. `thought_new` не создаёт определение. Старые команды `definition_save/publish/graph_checkout` оставлены для совместимости и диагностики, основной UI их не использует.

`GET /api/manage-index` возвращает технические ключи вида `node:ID`, `edge:ID`, `context:ID`, `scene:ID`, `object:ID`, `entry:ID`, `thought:ID`, `template:ID`, `definition:ID`, `workspace:ID`, `candidate:ID`, `designation:ID`, `link:SCENE/TARGET` и зависимости. `POST /api/manage-preview` принимает `mode: delete/reset`, `selection: [key]`, возвращает revision, selected, blocked, optional, counts, rewrites, зависимости и SHA-256 плана. `blocked` — недостающий транзитивный состав, а не автоматически удаляемый набор. `optional` — неиспользуемые экземпляры удаляемых мыслей, которые по умолчанию остаются. При reset выбран весь текущий индекс.

`manage_apply` требует `confirmed: true`, `previewRevision`, `previewHash` и тот же состав. Пересчёт и валидация выполняются внутри SQLite-транзакции; несовпадение, неполный выбор, stale revision или повреждение ссылок отклоняют запись целиком. Полный reset возвращает пустые канонические коллекции и operatorVersion=5; сцены/разборы исчезают из текущего snapshot. История и архивы импортов не стираются, Git и внешние SQLite не затрагиваются. Preview позволяет предварительно экспортировать состояние; restore остаётся возвратом полного снимка с сохранением последующей истории.

Пределы M019/сцен и 64 МиБ HTTP сохранены. Импорт по ID не объединяет конфликтующие значения. Расширение не включает автоматического определения тождества, смыслового сопоставления либо миграции активных контрактов при удалении постоянной структуры. [ADR M020](scenes-mvp.md#adr-m020-три-уровня-идентичность-и-управление-состоянием-15-октября-2026), [экспорт GUI](evidence/operator/export.json), [аудит](evidence/operator/verification.json).

## v4: ручной разбор и операторские шаблоны

M019 сохраняет прежний `format: concept-field-permanent`, `kind: graph`, snapshot-журнал и RFC6902-chain, добавляя необязательный корневой `thoughtLab`. Читатель принимает v1, v2, v3, v4. Экспорт выбирает минимально достаточную версию по **всей истории и импортным архивам**, поэтому restore к раннему состоянию не скрывает v4-строки. Без разборов/alias прежний граф экспортируется как v2, со сценами — v3. v3-документ с `thoughtLab` или `operatorAlias` отклоняется. Старые данные не переписываются при чтении; старое приложение не должно редактировать v4.

`node.operatorAlias` — необязательная рабочая подпись, максимум 1000 символов. `label` постоянного узла по-прежнему пуст; `designations` не создаются из alias. Структура узлов, обычных рёбер и направленного межрёберного контекста не меняется.

`thoughtLab = {drafts, templates, candidates, currentDraftId}`:

- `templates[]`: ID, название, версия, revision происхождения, `config` с `nodes`, `edges`, `contexts`. Значения элементов пустые. Сохраняется именно структура отношений по существующим постоянным ID, не множество названий и не классифицирующий концепт.
- `drafts[]`: ID, исходный `text`, `selection: [start,end]`, `anchors: [{id,start,end}]`, статус `draft/complete`, `config`, `templateRef: {id,version}` либо null, снимок `contract` либо null, `createdRevision`, `trace`. Индексы фрагментов — позиции Unicode code points, правая граница исключается. Явное уточнение оставляет `editingTemplateRef` и решение в trace, снимая контракт для последующего явного сохранения шаблона.
- `config.nodes[]`: локальный ID позиции, `conceptId`, `value`, `required`, `included`, необязательные координаты x/y. Локальный ключ действует внутри разбора; повторное применение адресуется парой draft ID / local ID, значения не копируются.
- `config.edges[]`: локальный ID использования, постоянный `edgeId`, точная `template`-подпись обычного ребра, локальные `from/to`, `required`, `included`, `activation: direct/context`. Включённые концы обязаны соответствовать постоянным концептам ребра.
- `config.contexts[]`: локальный ID, постоянный `contextId`, снимок `{id,from,to}` разрешения, локальные `from/to` **использований рёбер**, `required`, `included`. Ориентация сохраняется. Разрешение может быть включено, пока целевое использование исключено.
- `candidates[]`: ID, постоянные ordinary-edge `from/to`, ручное `reason`, `status: pending/accepted/rejected`, revision происхождения; решение дополнительно имеет `decision`, `decidedRevision`. Принятие проверяет наличие отдельно созданного разрешения, само не создаёт графовых объектов.

Контракт защищает обязательные ID, концепты, подписи рёбер, направление и концы; обычное сохранение не меняет выбранный шаблон. Незаполненная обязательная структура допустима для черновика, недопустима при завершении. Включённые необязательные элементы тоже требуют значения; исключённые не требуют. Доступность продолжения вычисляется из локальных привязок, не хранится как факт. `thought_step` повторно проверяет её и записывает trace. Сохранение формы не может назначить новую контекстную активацию.

Завершение атомарно добавляет объекты с **новыми сценическими ID**, `thoughtId`, `localId` и событие со ссылкой `thoughtId` в существующий `sceneLab`. У его утверждений сохраняются `activation`, `localId`, `thoughtId`, подпись постоянного ребра и конкретные концы. Разбор получает `sceneId`, `entryId`, `completedRevision`. Валидация сверяет значения/концепты/привязки и активации с разбором; подмена значений между экземплярами отклоняется. Завершённый разбор не перезаписывается обычными действиями.

`thought_*` используют одну revision-транзакцию PermanentStore. M018 проверяет весь итоговый граф: исчезнувшие/изменённые зависимости разбора или шаблона блокируют apply без частичной записи. Импорт добавляет точные ID и архив истории; конфликтующие записи не объединяются и не заменяются. Повторный импорт идемпотентен. Restore восстанавливает весь снимок, сохраняя более позднюю историю.

Пределы: 80 локальных элементов / 160 рёбер / 800 разрешений в конфигурации; 1000 записей каждого вида; 10000 текстовых соответствий; прежний HTTP-предел 64 МиБ. Полная схема и ограничения смысла — [ADR M019](scenes-mvp.md#adr-m019-ручной-разбор-и-операторские-конструкции-15-октября-2026), первичный пример — [экспорт GUI](evidence/thoughts/export.json).

## M018: транзакционные правки и baseline области

Канонические коллекции, SQLite и JSON v2 сохранены; текущий reader принимает прежние v1/v2 без миграции и сохраняет исходную историю. В рабочих definitionDrafts добавлены необязательные `graphBase: {nodes,edges,contextEdges}` и `graphStale: string`. Baseline содержит только выбранные исходные объекты, ограниченные прежними лимитами черновика; designations редактируются независимыми явными действиями. Он нужен для сравнения с актуальным графом, не публикуется вместо канонических коллекций и не участвует в обходе графа. Рабочая и исходная версия экспортируются вместе с полным журналом; незавершённость и конфликт переживают restart/import.

`graph_checkout {nodeIds}` сохраняет область (1–80 различных ID, все внутренние рёбра и их внутренние context-пары). Чистая область того же набора открывается повторно без нового draft ID. `POST /api/graph-preview {operations,definitionId?}` возвращает revision и полные before/after ID, индексы определений, затронутые context-пары и черновики. `graph_apply {operations,definitionId?,confirmed:true,previewRevision}` требует актуальные общую revision и previewRevision; максимум 1000 явных операций. Put редактирует объект прежнего ID; новое создание требует сохранённый definitionId происхождения. Delete не выполняет каскад. Redirect содержит source/target, uses [{id,end:from|to}], designationIds, definitionIds и deleteSource; все выборы явные. Все изменения проходят общий validate_graph до SQLite commit.

`definition_publish` области вычисляет тот же общий transaction patch. Подтверждённая область записывает index publication выбранных IDs; исходный текст остаётся свидетельством ввода, не новым толкованием каждого объекта. Старые owner-публикации сохранены для совместимости рабочего процесса, но внешне изменённый собственный объект ставит постоянный барьер graphStale. Обновление чужого выбранного base после просмотра остаётся допустимым. Сохранение устаревшей вкладки не снимает барьер и не заменяет её старый baseline свежим без проверки.

История graph_apply хранит подробный diff в journal.detail и полный snapshot стандартным способом; локальное restore создаёт новую revision и сохраняет последующую историю. Геометрия, origins существующих объектов и UUID не пересоздаются при перенаправлении. Publications — актуальные индексы ID, поэтому их списки меняются в той же транзакции; исторические snapshots/исходные тексты неизменны. Прежние версии приложения не поддерживают защиту M018: открывать новые рабочие черновики для редактирования нужно актуальной версией, безопасность downgrade не заявляется. Проверки — [M018](composition-verification.md#m018-единый-редактор-постоянного-графа-15-октября-2026).


## M017: маркеры и гибкие линии без изменения формата

Квадрат relation ID, половина длины Bezier, SVG сегменты, диагностика обхода, выбор/hover и режим маркеров вычисляются клиентом. Их нет в nodes/edges/contextEdges, JSON v2, SQLite или journal snapshots. `contextEdges.from/to` сохраняют ordinary ID; `role:component` исключён. Новых conceptual nodes/relation IDs нет. Существующий JSON M015 импортирован без изменений, новая межопределительная пара публикуется штатным способом; экспорт/import/restart и архивная история сохраняют точный state. Backend побайтно прежний относительно M016 `2fde7df`. См. [проверки M017](composition-verification.md#m017-маркеры-рёбер-и-гибкий-контекст-14-октября-2026).

## M016: происхождение без расширения хранения

Формат JSON v2, поля state и SQLite прежние. UI читает `nodes[].origins[].definitionId/snapshot.definition/snapshot.source`, а по definitionId получает текущее title публикации либо сохранённого черновика. `definitionPublications[].nodeIds` фиксирует подтверждённое использование ID; текст/source берутся из самой публикации, не дублируются в каждом узле. Сохранённые черновики показываются отдельно от опубликованных данных. Вычисленный HTML/краткий текст не экспортируются.

Исправление потери происхождения: повторная публикация владельца сохраняет прежний origins собственного существующего узла, вместо его замены новой редакцией определения. Пустой origins тоже сохраняется; отсутствие свидетельства не заполняется текущим текстом. Новый узел получает прежний стандартный снимок. Геометрия, владение, UUID, обозначения, reuse и состав не меняются. Уже заменённые до M016 снимки остаются как сохранены; автоматического обращения к архивной истории/миграции нет. Первоначальный title в прежнем snapshot не хранился, поэтому UI честно помечает текущее название. Полный state и архив исходного журнала сохраняются при restart/export/import; проверка — [M016](composition-verification.md#m016-информативный-выбор-существующих-концептов-14-октября-2026).

## M015: геометрия без смены JSON v2

FORMAT/VERSION и коллекции state остаются прежними. В node изменяются только x/y и существующий необязательный геометрический признак layoutPinned:true (false снимает поле). Радиус, степень, круглая форма, режим подписи, ранги/подсветка и preview не сериализуются. Экспорт/import/restart сохраняют координаты и закрепление вместе с полной историей; старые v1/v2 без pin подходят без миграции.

Новые защищённые действия: layout_pin {nodeIds,pinned}; layout_apply {positions:{id:{x,y}},algorithm:force|hierarchical|radial,previewRevision,confirmed:true}; layout_restore {confirmed:true}. Действует актуальная revision; координаты конечны в ±100000, карта до 10000 IDs, закреплённые/отсутствующие IDs и наложения перемещаемых окружностей отклоняются атомарно. Для undo before/after/algorithm записаны JSON-строкой в существующем journal.detail; сам state не получает lastLayout. Это метаданные подтверждённой геометрии, не второй граф. Undo возвращает только xy при неизменённых затронутых позициях/закреплении; после import/общего restore/предыдущего undo нужна история или новая раскладка. Архив исходного журнала сохраняет все эти detail и snapshots, но не подменяет локальную команду undo.

## M014: подписи без изменения JSON v2

Вычисляемые строки `{Стержень, Головка}` / `{Деталь, {Стержень, Головка}}`, сокращения и #токены являются только представлением. Их нет в node.label, designations, definitionDrafts/Publications или history. VERSION=2, парсер, валидатор компонентности, UUID, транзакции и shape state остаются побайтно прежними относительно M013. Экспорт/import/restart восстанавливают реальные компоненты/обозначения; UI заново вычисляет подписи. Поле labels ответа словарного поиска не содержит производных форм; найденные по компонентам безымянные α могут иметь labels:[] и показываются клиентским индексом. Это контракт поискового представления, не расширение постоянного формата и не автоматическое значение слова.

## Активный контракт M013: v2 с α

Экспорт теперь `{format:"concept-field-permanent",version:2,kind:"graph",state,historyEncoding:"rfc6902-chain-v1",history,exportedAt,importedHistory?}`. Набор коллекций и SQLite-журнал прежние. Разделы M008–M012 ниже описывают исторический v1; новый reader принимает v1 и v2, включая все snapshots/patches и плоские архивы истории. α в документе, помеченном v1, отвергается. Отсутствие α не требует изменения существующей SQLite или её ревизий; новые exports всегда v2.

Node допускает `structure:"concept"|"alpha"`; у обеих структур собственный ID, `designationOnly:true`, `label:""`, origins, definitionId и координаты. Alpha не требует kind/notes или designation. Designation.target может адресовать α; название определения не является словарным обозначением α.

Edge допускает `role:"relation"|"component"`. Component.from обязательно адресует α, component.to — любой существующий concept/alpha. Каждый edge имеет свой ID/происхождение и принадлежит одному создавшему определению. Повтор прямой пары компонентности, self-loop/косвенный цикл, исчезнувший ID и пустая опубликованная α недопустимы. Проверка циклов итеративна; её отдельная проба — 1500 уровней. Это не измерение полного GUI/import на такой глубине. Обычные отношения могут соединять любые концептуальные ID, включая α, и могут иметь прежние циклы. Никакого переноса отношения от компонента к целому нет.

Draft.nodes имеют необязательные structure (по умолчанию concept), kind, notes; существующий ID сохраняет base и исходные поля. Draft.edges имеют необязательный role (по умолчанию relation). Прямые endpoints выбираются в nodes этого черновика; состав выбранной существующей α остаётся в общем графе, раскрывать/копировать потомков для reuse не нужно. Неполную новую α разрешено сохранить в черновике; цикл/повтор прямого компонента отвергается уже при save, совместная целостность всех определений — при prepare/publish.

Publication.edgeIds содержит только relations; необязательный componentIds — IDs явно выбранных обязательных включений. Routes/contextEdges адресуют только relations. Ссылка другой публикации на узел/ребро блокирует удаление; чужая α редактируется через определение происхождения. Preview и publish используют одну prepare, все отказы атомарны. При изменении выбранного node.base оператор просматривает объект и явно обновляет выбранный ID в форме, сохраняя его и рёбра.

## Отображение M012 без изменения формата

Прямоугольные контекстные трассы, порты и SVG marker вычисляются из текущих координат узлов и ordinary ID ссылок. Они не добавляют полей в state/contextEdges, черновики, историю или экспорт. Версия по-прежнему v1; прежние документы сохраняют IDs/from/to и получают новый показ после открытия. Не проложенная из-за перекрытий/лимита линия остаётся записью и доступна по ID. Отображение не добавляет допустимых пар, веса или активацию.

## Дополнение M009: редактируемые обозначения

Версия остаётся v1: расширения необязательные, прежние exports/drafts допустимы. Designation имеет собственный неизменяемый id, target — ID концепта, text — внешнюю форму. Повторы текста между IDs и внутри одного ID (например, разные значения) допустимы; равный текст не объединяет объекты. notes и необязательный lexicalSource сохраняют различия значений. lexicalSource включает name и необязательные lemma/entry/senseId/revision/revisionUrl, исходный текст/лицензию/атрибуцию/контрольную сумму из выбранного толкования. Без источника допустимо ручное соответствие. Удаление последней designation не удаляет node: показывается ID.

Новое поле черновика может содержать designations:[{id,text,notes?,lexicalSource?}]; ID соответствия переходит в граф при подтверждении. Отсутствие списка совместимо с M008 designation (одной первоначальной подписью). После публикации списки черновика — исходное свидетельство, не предписание текущим соответствиям. prepare сохраняет все текущие обозначения оставшихся узлов; только удаление самого собственного концепта при подтверждённой правке миниграфа удаляет его входы. Прежние защищённые ссылки других публикаций по-прежнему блокируют такое удаление.

Действия designation_save {nodeId,designationId?,text,notes?,lexicalSource?} и designation_remove {designationId} доступны через защищённый /api/action с актуальной revision. target существующего соответствия не меняется: другой ID требует отдельного соответствия. Каждая правка сохраняет собственный ID обозначения и не меняет nodes/edges/contextEdges/drafts/publications. Удаление фиксируется в журнале; вернуть его можно общей историей. Импорт остаётся точным по ID: конфликт правки не заменяет текущую запись молча.

`source.responseSha256` — SHA-256 нормализованного JSON-ответа API: `json.dumps(result, ensure_ascii=False, sort_keys=True).encode('utf-8')`, не checksum транспортного сжатого потока. RevisionUrl/номер редакции позволяют получить исходное содержание; fetchedAt фиксирует конкретное получение.

История входных документов сохраняется в `permanent_imports` по SHA-256 документа, в той же SQLite, и возвращается при экспорте как необязательное `importedHistory`. Вход содержит локальную историю источника; она проверяется и архивируется, не заменяя номера текущего журнала и не создавая второго активного графа. Повторный документ не создаёт второй архив. Архивы плоские, без вложенных importedHistory; действует общий предел входного документа 64 МиБ. Это сохранение уже полученной истории, не механизм сопоставления/разделения источников. При повторном экспорте исходная история остаётся доступна в JSON. Рост архива не очищается автоматически; больших коллекций импорта эта проба не измеряла.

Активный экспорт: `{format:"concept-field-permanent",version:1,kind:"graph",state,historyEncoding:"rfc6902-chain-v1",history,exportedAt}`. Это один граф, не workspace независимых studies. В `state` ровно nodes / edges / designations / contextEdges / definitionDrafts / definitionPublications. Пустой граф валиден без rootId. Базовые поля узлов и черновиков/маршрутов сохранены из [M007 v4](data-format-v4.md), но нет accumulation/manual/sources/decisions/nodeIds карт копий.

Новые концепты имеют один UUID, `structure:concept`, `designationOnly:true`, пустой label и внешнее designation `{id,target,text,...}`. Обычное ребро `{id,from,to,role:relation,...}` ссылается на ID концептов. Контекстное `{id,from,to,definitionId}` — на два разных обычных ребра; пара направлена и уникальна. DefinitionId в origins/объекте указывает происхождение создания, а не самостоятельный подграф. Сохранённые drafts/publications адресуют те же IDs и не копируют объекты. IDs всех актуальных концептов/рёбер/контекстов/обозначений/определений глобально различаются; повторы ссылок черновика допустимы как ссылки.

Определение может хранить `source`: name, url, revision, revisionUrl, retrievedAt, license, licenseUrl, attribution, responseSha256, transformation, lemma, senseId, entry, originalText и operatorEdited. Выбранное толкование остаётся черновиком до ручного построения/подтверждения. Если оператор меняет текст, исходный текст/редакция сохраняются и правка отмечается. Публикация и origins сохраняют этот источник.

Сохранение выполняется транзакционно в `permanent_revisions`, отдельном журнале в существующей SQLite. Доступ к старой `revisions` сохраняется только в историческом режиме; это защищённый архив, не часть нового графа. При первом открытии старой базы backup всей SQLite выполняется до CREATE/INSERT новой таблицы, включая WAL; проверяются integrity, SQL digest, SHA-256 копии. Манифест хранится рядом с backup и в init.detail новой истории. Восстановление старой базы выполняют на копии backup через `--legacy`.

Preview и включение используют одну функцию prepare M007 с прямым каноническим набором вместо проекции. `definition_save` сохраняет черновик, `definition_publish` требует confirmed:true и актуальную revision. Повтор не создаёт новых объектов. Чужие подтверждённые ссылки защищены, поэтому удаление их объекта блокирует всю транзакцию. Конструктор изменяет только объекты своего создания; повторно выбранный ID сохраняет исходные поля. Опубликованные списки ссылок — происхождение/защита ручной работы, не границы обхода графа.

Импорт проверяет snapshot и всю history. В чистой базе структура сохраняется точно. В непустой базе добавляются отсутствующие IDs, равные повторы пропускаются, конфликт по ID/составу определения отклоняется целиком. Отсутствие объекта во входе не удаляет старый объект. Для иных изменений используйте конструктор или explicit restore своей локальной версии после резервного экспорта. Imported history переносится в самом документе, но не подменяет локальные номера версий: локальная история фиксирует подтверждённый импорт. Старые concept-field-graph v1–v4 явно отвергаются новым режимом, доступны через --legacy; автоматического переноса нет.


## v3: сцены и рабочие экземпляры

MVP от 15 октября 2026 добавляет необязательный `state.sceneLab` с `scenes`, `workspaces`, `currentSceneId`. Поля прежнего каркаса не меняются. Полная модель и принятое решение — [scenes-mvp](scenes-mvp.md). Это отдельная ответственность нового раздела, не перенос исторических исследований в постоянные факты.

Экспорт использует v3, если сцены есть в текущем снимке, любом снимке его истории или импортном архиве v3. Поэтому восстановление состояния до первой сцены не скрывает более позднюю историю под версией v2. Прежние данные без сцен по-прежнему экспортируются v2. Принимаются v1/v2/v3, но `sceneLab` запрещён в v1/v2, в том числе в истории. Компрессия SQLite и `rfc6902-chain-v1` прежние; новые таблицы не нужны.

Валидация проверяет ID, ссылочную целостность сцен, тип назначения, концепты объектов, совпадение концов и снимка отношения, адреса снятий, происхождение рабочих заполнений, независимость локальных ID и обязательный состав копий. Операции сцен используют общую проверку revision; отказ оставляет весь снимок/журнал неизменными. Изменение или удаление используемого сценой отношения, удаление концепта, нарушающее ссылки, блокируются. Рабочие снимки структуры не сравниваются с новой версией характеристик каркаса: это независимые исторические копии.

Импорт добавляет отсутствующие сцены/области по точным ID и отклоняет различающиеся записи с одним ID. Текущий разговор сохраняется у получателя, если уже выбран; иначе берётся из импорта. Полное восстановление заменяет `sceneLab` вместе с графом. Старый клиент v2 не должен читать v3; обратный экспорт сцен в v2 не предусмотрен.


### Уточнение v3 после external review 78002f2

Объект сцены может дополнительно содержать `contentConceptId` — устойчивый ID содержательного концепта/α существующего каркаса. `conceptId` по-прежнему задаёт позицию шаблона и проверяется по его концам. Отсутствие нового поля сохраняет прежнюю модель без предположения содержательной идентичности; никаких привязок по строке или общей роли не вычисляется. Поле хранится в сцене и рабочей копии; структура копируется от содержательного корня, если он указан, иначе от прежнего `conceptId`. Валидация проверяет существование содержательного ID, его сохранность в происхождении копии и соответствие её корня. Удаление используемого содержательного концепта отклоняется.

Действующий контекст не хранится вторым полем в сцене: это `contextSceneId` последнего входа `kind=context`. `links` остаётся списком накопленной доступности. Команда `scene_context` принимает необязательный явный `contextSceneId` вместе с исходным текстом; без ID сохраняется точный поиск обозначения. `/api/state` и ответы мутаций дополняют вычисляемое `sceneView` полями `activeContext` и `contextSources`, не записывая их в экспорт. Контекстный вход допустим только в разговоре с целью назначения knowledge.

Это совместимое чтение прежних v3 снимков/истории текущим кодом, не изменение/миграция исходных файлов. Предыдущий бинарный MVP не реализует дополнение и не предназначен для редактирования новых содержательных привязок. Сопоставление независимых сцен и новые правила локального перехода форматом не вводятся. Решение и последствия — [ADR MVP-S2](scenes-mvp.md#adr-mvp-s2-содержательная-привязка-и-действующий-контекст-после-review-78002f2).
