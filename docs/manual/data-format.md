# JSON обмена графами, версия 1

Это описание прежней версии; текущий экспорт — [v2 с комбинациями и словарём](data-format-v2.md). Импорт v1 сохраняется, прежние данные и история не переписываются.

Общий заголовок: `format: "concept-field-graph"`, `version: 1`, `kind`. Код приложения не обращается к сетевым схемам, LLM или внешней онтологии. Предлагаемый ниже формат принят для этого инструмента; это инженерное решение, не гипотеза о представлении человеческого знания.

## Виды документов

| `kind` | Назначение | Основные поля |
|---|---|---|
| `workspace` | Всё пространство / резервная копия | `state`, `historyEncoding`, `history`, `exportedAt` |
| `study` | Одно исследование полностью | те же + `selection` |
| `fragment` | Узел и окружение | те же + `selection.nodeId`, `selection.depth`, `selection.sourceRootId` |
| `changes` | Отдельные предложения изменения | `changes` |
| `diff` | Отчёт о различиях | `left`, `right`, `correspondences`, `aligned`, `onlyLeft`, `onlyRight`, `edges`, `relationAlignments`, `versionChanges` |

Неизвестные версии и виды отвергаются. `diff` не импортируется как доказательство соответствия. В версионном diff `versionChanges` — готовый самостоятельный документ `changes`, с исходным `base`. В независимом diff этого пакета нет: одна структура не считается новой версией другой.

## Пространство и идентификаторы

`state` содержит четыре списка: `studies`, `matches`, `imports`, `proposals`. В исследовании обязательны `id`, `title`, `description`, `rootId`, `nodes`, `edges`, `archived`, `createdAt`. Названия не уникальны. ID — непустые строки до 200 символов, глобально уникальные внутри пространства; приложение генерирует UUID4. Источник обмена должен создавать новые ID для новых объектов и сохранять прежние для продолжения тех же объектов. Тестовые фикстуры используют детерминированные UUID5.

Узел:

```json
{
  "id": "5d93e746-8c54-4ba7-931c-3f2ddad7e139",
  "label": "твёрдый",
  "kind": "свойство",
  "notes": "Пояснение оператора",
  "alternatives": "Неоднозначность или альтернативы",
  "source": "Источник / обоснование",
  "origins": [],
  "createdAt": "2026-10-09T00:00:00+00:00"
}
```

`label` обязателен; `kind` свободный, может быть пустым. Поля `label`, `kind` ограничены 1 000 символами, содержательные поля — 50 000. Все пять строковых полей и список `origins` присутствуют в экспортированном графе. Дополнительные JSON-атрибуты сохраняются при обмене и редактировании обычных полей интерфейса. Необязательные `x`, `y` задают сохранённую позицию. Интерфейс не выводит произвольные дополнительные атрибуты как поля формы; их можно видеть в экспорте / просмотре предложений. Для обычного ручного описания используйте поля содержания и связанные узлы.

Отношение:

```json
{
  "id": "f2815a13-a6ad-4f62-83fc-2536b61cd738",
  "from": "ID-начала",
  "to": "ID-конца",
  "type": "имеет свойство",
  "notes": "Контекст интерпретации отношения",
  "origins": []
}
```

Оба конца принадлежат этому исследованию. Тип — непустая свободная строка до 1 000 символов. Допускаются параллельные отношения и циклы. Нет встроенной иерархии отношений или начального набора примитивов. Объекты разных исследований связываются через `matches`, а не обычным ребром.

Соответствие содержит `id`, `leftStudy`, `leftNode`, `rightStudy`, `rightNode`, `status` (`pending`, `confirmed`, `rejected`), `reason`, `decidedAt`. Для одной неориентированной пары узлов хранится одно актуальное решение; прежние решения доступны в истории. `matches` в экспорте одного исследования / фрагмента включаются только при наличии **обоих** концов; межисследовательские соответствия целиком доступны в экспорте пространства и diff.

## Происхождение

После объединения `origins` каждого узла содержит `studyId`, `studyTitle`, `nodeId`, `capturedAt` и полный `snapshot` исходного узла с его собственным происхождением. Отношения аналогично сохраняют `edgeId` и снимок. Снимки не подменяются последующим изменением исходников.

Исследование объединения содержит `merge.sourceStudyIds`, выбранные `matchIds`, `nodeMap` (старый ID → новый ID), `decisions` (снимки выбранных ручных решений). Объединённые элементы получают **новые** ID, поскольку принадлежат новой структуре; импорт готовой структуры сохраняет эти ID. Пояснения, источники и альтернативы отождествлённых элементов объединяются с подписями источников, полные оригиналы остаются в снимках. Все отношения копируются отдельно без автоматического отождествления.

`imports` хранит исходный `document`, время, ID импорта и SHA256 `fingerprint`. `proposals` хранит кандидатов и решения об их принятии / отклонении, исходный `base`, связь `importId`, время и обоснование review. Экспорт исследования / фрагмента фильтрует архив импорта по выбранному исследованию и узлам; пометка `scope` сообщает об этом. `fingerprint` идентифицирует полный первоначальный документ. Узловые `origins` намеренно содержат полные снимки релевантных источников, даже если предок снимка не входит в окружение; произвольные чужие исследования в архив фрагмента не включаются. Полная исходная копия импорта доступна в резервной копии пространства.

## История и восстановление версий

SQLite хранит атомарные сжатые снимки локального пространства с монотонным `revision`. История JSON экспортируется компактно:

```json
{
  "historyEncoding": "rfc6902-chain-v1",
  "history": [
    {
      "id": 0,
      "time": "2026-10-09T00:00:00+00:00",
      "action": "init",
      "detail": "Создано рабочее пространство",
      "patch": []
    }
  ]
}
```

Начальная база цепочки — `{"studies":[],"matches":[],"imports":[],"proposals":[]}`. Последовательно применяйте `patch` каждой строки к предыдущему состоянию. Это подмножество JSON Patch: `add`, `remove`, `replace`; пути — JSON Pointer с экранированием `~0` и `~1`. Номера записей возрастают; в отфильтрованном экспорте допустимы пропуски. Полученное последнее состояние должно совпадать с полем `state` документа. Неповторяющееся содержимое импорта сохраняется в цепочке, без копирования каждого неизменившегося графа на каждый шаг.

Функции `app.journal.expand_history(document)` и `apply_patch(state, operations)` позволяют восстановить версии в Python. `expand_history` выдаёт записи с полным `state` последовательно, а не загружает все версии одновременно. Для маленьких исходных фикстур импорт также принимает строки истории с явным `state`. Неизвестная кодировка, повреждённые пути и несовпадение последней версии отвергаются.

Импортированная история хранится как архив с исходной нумерацией; локальный журнал не перенумеровывается чужими записями. Принятие кандидатов создаёт новые локальные записи. Внешние `confirmed` / `rejected` соответствия при применении становятся `pending`; оригинальное решение остаётся в архиве и нуждается в ручной проверке.

## Пакет предложений `changes`

Минимальный пример ответа ChatGPT для раскрытия известного узла:

```json
{
  "format": "concept-field-graph",
  "version": 1,
  "kind": "changes",
  "changes": [
    {
      "operation": "node",
      "studyId": "ID-исследования",
      "base": null,
      "value": {
        "id": "НОВЫЙ-уникальный-ID-узла",
        "label": "Новое пояснение",
        "kind": "определение",
        "notes": "Предложенное содержание; требует проверки",
        "alternatives": "",
        "source": "Предложение ChatGPT",
        "origins": []
      }
    },
    {
      "operation": "edge",
      "studyId": "ID-исследования",
      "base": null,
      "value": {
        "id": "НОВЫЙ-уникальный-ID-отношения",
        "from": "ID-раскрываемого-узла",
        "to": "НОВЫЙ-уникальный-ID-узла",
        "type": "раскрывается через",
        "notes": "",
        "origins": []
      }
    }
  ]
}
```

Операции `study`, `node`, `edge`, `match` означают создание или замену указанного объекта. `study.value` содержит метаданные исследования без `nodes` и `edges`. Для редактирования `base` — **полный исходный объект**, `value` — его предложенная новая версия с тем же ID и дополнительными атрибутами. Для создания `base:null`. Без `base` изменение существующего объекта всегда считается конфликтом.

`delete_node` и `delete_edge` имеют `value:{"id":"..."}` и полный исходный объект в `base`. Удаление узла также удаляет инцидентные отношения и соответствия. Не допускается удаление корня. После удаления связанного узла не импортируйте отношения, ссылающиеся на него.

Кандидат `match` не требует `studyId`, потому что у него два исследования. Его статус после применения будет `pending`; смысловое подтверждение производится в сопоставлении.

Отсутствующие строковые поля нового узла дополняются пустыми строками, `origins` — пустым списком, `createdAt` — временем принятия. У существующего узла принятые `origins` сохраняются и дополняются, даже если предложение их опустило. Существующие произвольные атрибуты должны входить в `value`, иначе явная замена объекта может убрать их; прежняя версия остаётся в истории. Отсутствие узла в документе графа **не** означает удаление.

Строки одного документа не должны несколько раз менять один объект. При очереди разных альтернатив одного объекта примите только одну. Зависимости применяются в порядке исследование → узлы → отношения → соответствия → удаления; пакет проверяется целиком. Сохранение осуществляется транзакцией, при ошибке нет частичного применения. `base` проверяется повторно на момент принятия, а не только при загрузке.

Повторный импорт того же содержимого без изменения `exportedAt` даёт ноль новых кандидатов. Точно совпадающие объекты с теми же ID пропускаются и в другом документе. Иные значения под тем же ID показываются как конфликт; коллизия с ID другого типа / исследования не может быть разрешена заменой. Кандидаты, уже ожидающие решения с тем же предложением, не дублируются. Отказ не стирает запись рассмотренного импорта; для пересмотра используйте восстановление версии перед рассмотрением или новый изменённый пакет.

## Анализ различий

Версии одного исследования сопоставляются по ID; проверяются **все** атрибуты, включая происхождение и позиции. Независимые исследования используют только ручные `confirmed` соответствия; допускаются несколько соответствий одному элементу. `aligned` перечисляет равные поля и различия, `onlyLeft` / `onlyRight` — элементы без подтверждённого соответствия. Эти поля не объявляют несопоставленные элементы смыслово разными.

`relationAlignments` перечисляет структурно похожие отношения: подтверждённые концы и точное равенство типа, отдельно различия пояснений. Это не решение о тождестве отношений. `edges.onlyLeftIds` / `onlyRightIds` сравнивают исходные ID, которые у независимых исследований различаются даже при структурном сходстве. Полные `left` / `right` позволяют выполнить иной автоматический анализ, сохранив все исходные материалы и решения.
